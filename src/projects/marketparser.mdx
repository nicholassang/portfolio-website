## Goals

The goal of this project was to build a simplified version of the infrastructure used in electronic trading systems by implementing a low-latency market data processing engine in modern C++20. The system simulates a complete market data pipeline consisting of:

- **Zero-copy packet decoding**
- **Custom memory allocation**
- **Lock-free communication**
- **Order book updates**

---

## Key Concepts Explored

### Cache Efficiency

Modern CPUs are extremely fast, but memory access can become the bottleneck. This project focused on:

- Contiguous memory layouts
- Minimizing allocations
- Reducing unnecessary copies
- Cache-friendly data structures

### False Sharing

False sharing occurs when multiple CPU cores modify variables located on the same cache line, causing performance degradation. This project avoided these issues through:

- Careful memory layout
- Separating frequently modified variables
- Understanding cache line boundaries

### CPU Affinity and Thread Scheduling

To reduce latency variance, the project used CPU affinity to:

- Pin threads to dedicated cores
- Avoid unnecessary context switches
- Improve cache reuse

### Memory Management

General-purpose allocation introduces unpredictable latency. Instead, this project implemented a custom memory pool with:

- Preallocated memory
- Object reuse
- Constant-time allocation

## Implementation

### Zero-Copy Packet Parser

The parser avoids unnecessary data movement by interpreting incoming market packets directly from raw buffers. It uses:

- Packed structures
- Direct memory access
- Binary decoding

### Packet Memory Pool

To avoid latency variation from repeated heap allocation, a custom memory pool was implemented. Features include:

- Preallocated packet storage
- Object reuse
- Constant-time acquire/release

Example:
```cpp
auto* packet = pool.acquire();
process(packet);
pool.release(packet);
```

### Lock-Free SPSC Queue

The pipeline uses a Single Producer Single Consumer (SPSC) queue for communication between processing stages. Design goals:

- No locking
- Predictable latency
- Minimal synchronization overhead

### Order Book Engine

The order book maintains current bid and ask levels. Supported operations include:

- `addBid(price, quantity)`
- `removeBid(price)`
- `bestBid()`

The design builds upon lessons from the previous order book project, optimizing for:

- Contiguous memory structures
- Cached best prices
- Optimized lookups
